## 1. Core vision

M99 Knowledge Platform is not a scraper and not a single-site uploader. It is the canonical identity, verified product knowledge, supplier/manufacturer evidence, content/SEO, publishing, synchronization, ERP/CRM integration, audit and governance layer for the M99 ecosystem.

M99 owns:

- canonical product identity;
- governed product facts;
- source/evidence provenance;
- supplier mappings;
- manufacturer mappings;
- channel-specific content;
- controlled publishing decisions;
- audit history.

External systems are evidence sources, commercial sources, channels, destinations, operational systems or migration/reconciliation sources.

Dolibarr remains the intended operational ERP/CRM/warehouse representation. M99 remains the canonical knowledge/governance layer.

## 4. Canonical product and evidence model

The platform separates:

`ProductGroup -> Product -> Channel`

and separately governs:

`Supplier -> SupplierMapping -> Supplier Reference`

`Manufacturer -> ManufacturerMapping -> Manufacturer MPN`

Supplier and manufacturer codes may have identical characters but remain different semantic roles.

A supplier reference may seed manufacturer discovery but cannot verify Manufacturer MPN by itself.

Canonical channel reference for PrestaShop should be the permanent M99 reference.

## 5. Content and SEO governance

The platform is designed for multilingual, channel-specific content.

Current language registry direction:

- m99.eu: EN / BG / RU;
- mela99.com: BG / EN;
- laviro.ro and alviro.ro: RO / EN;
- BG WordPress channels: BG;
- future languages are registry-driven, not globally hardcoded.

Content assets include Product Name, H1, optional semantic H2-H5, Short Description, Long Description, technical specifications, FAQ, Meta Title, Meta Description, keywords, localized ALT text and Product schema.

`CONTENT-EDITORIAL-001`:

- model-assisted writing is allowed;
- the model is never the factual source of truth;
- unsupported claims are blocked;
- detector evasion is not a quality objective;
- originality, usefulness, factuality and natural language are quality objectives;
- Meta Description and Short Description are distinct assets in every language;
- normalized Meta-vs-Short similarity must be `< 0.75`; exact `0.750` blocks.

## 6. Release engineering constitution

`REL-SELFTEST-001` and later extensions establish:

- internal RC before operator delivery;
- maximum practical local/static/mocked simulation;
- AST/compile checks;
- symbol/namespace sanity;
- helper/runtime dependency execution;
- mocked success and failure paths;
- package-local and repository-root execution contexts;
- exact runtime route graph verification for FastAPI;
- no weakening/skipping/xfail merely to get green;
- transactional rollback on failure;
- Windows/CMD is final real-environment acceptance, not first-line debugging;
- consolidate fixes rather than long tiny-hotfix chains.

Git governance `RELEASE-GIT-002` requires after an accepted milestone:

`Git audit -> maintained regression -> secrets guard -> git diff --cached --check -> exact staging -> commit -> push -> verify HEAD == origin/main -> record SHA`.

Runtime DBs, sidecars, backups, caches, temporary output, credentials and installer ZIPs are not automatically source code and must not be blindly committed.

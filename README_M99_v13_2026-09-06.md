## 1. Vision and role of M99 Knowledge Platform

M99 Knowledge Platform is not a product scraper or a single-site uploader. It is the canonical identity, verified product knowledge, supplier/manufacturer evidence, commercial intelligence, content/SEO, publishing, synchronization, ERP/CRM integration, audit and governance layer for the M99 ecosystem.

M99 owns canonical identity and governed verified knowledge.

External systems are classified as:

- evidence sources;
- commercial sources;
- channels;
- destinations;
- operational systems;
- migration/reconciliation sources.

Dolibarr is the operational ERP/CRM/warehouse representation. It does not own canonical M99 identity.

Core principles:

- Single Source of Truth.
- Knowledge First.
- No Duplicate Data.
- Evidence Based.
- AI Native, not AI Invented.
- Historical observations are preserved.
- Market and Channel are separate concepts.
- Observation is not automatically canonical truth.
- Removing a product from one channel must not destroy accumulated M99 knowledge.
- A new feature must not break an already accepted guardrail.

## 4. Canonical product and identity model

Canonical chain:

`ProductGroup -> ProductVariant -> SupplierOffer / SupplierMapping -> Evidence / Observation -> ChannelPresence -> ChannelContent -> ChannelPrice -> InventoryMapping`

External identifiers are mappings, not canonical identity:

- supplier reference / SKU;
- manufacturer reference / MPN;
- EAN / GTIN;
- MoneyWork code;
- Dolibarr ID;
- website/channel product ID;
- marketplace ID;
- legacy reference;
- title;
- URL.

Identity resolution:

`External Record -> Import -> Normalize -> Resolve -> Match -> Decision -> Overrides -> Operator Review -> Final M99 Identity`

Identity states:

`NEW / EXISTING / AMBIGUOUS / UNRESOLVED`

`AMBIGUOUS` requires a human decision.

M99 Reference:

`M99-` + digits only.

Assigned M99 identity is never reused for another ProductGroup.

Identity Before Content:

`SELECT -> RESOLVE IDENTITY -> LINK EXISTING or CREATE PERMANENT M99 ID -> THEN CONTENT`

## 5. ProductGroup lifecycle and destructive actions

ProductGroup lifecycle is fixed:

`draft -> active -> paused -> retired`

Hard DELETE remains possible only as an exceptional governed operation requiring:

1. operator approval;
2. explicit manual `DELETE` confirmation;
3. audit logging.

Normal lifecycle transitions are preferred over physical deletion.

## 6. Organization, Supplier, Manufacturer and Brand governance

Supplier and Manufacturer remain separate governed roles of canonical Organization.

One Organization may have both roles, but the roles are not silently interchangeable.

Brand is a separate canonical object.

An operator may propose a new Supplier, Manufacturer or Brand. A proposed object remains pending until Super Admin governance.

Only Super Admin may perform governed approval actions such as APPROVE, REJECT, MERGE_WITH_EXISTING or ACTIVATE_ROLE.

Supplier-provided manufacturer/brand text is evidence only. It must not silently become an approved canonical Manufacturer.

One canonical M99 product may have multiple verified SupplierMappings and Manufacturer mappings.

The system must never assume:

`one product = one supplier`

## 12. Content, SEO and language policy

Content Engine operates on verified Product Knowledge.

Supplier prose is not copied verbatim.

Facts may be shared, but prose and SEO are adapted by market/channel/language.

A complete publishable package may include:

- Product Name / H1;
- short and long descriptions;
- H2/H3;
- technical specifications;
- materials;
- sizes;
- FAQ;
- Meta Title;
- Meta Description;
- SEO keywords;

- images;
- localized ALT.

AI may structure, translate and adapt verified facts. It must not invent technical claims, standards, stock, materials or unsupported marketing claims.

## 14. Variants and stock semantics

Visible size != stock.

Supplier availability != M99-owned physical stock.

Channel-published sellability is also separate.

For a variational product, exactly one default combination is required.

Supplier/manufacturer external availability may be represented separately from M99 physical stock, including variant-aware external warehouse semantics in Dolibarr.

M99 must never fabricate numeric supplier quantity such as 30 or 999 merely because a product appears in stock.

---

## 15. Product Presence and Daily Sync

Presence != Stock.

Product Presence answers where a canonical product exists or is missing and may preserve external IDs, publication state, last verification and sync state.

NEW PRODUCT IMPORT and EXISTING PRODUCT DAILY SYNC are separate operational classes.

Daily Sync contract:

`Verified SupplierMapping -> Observation -> Compare Last Verified -> Change Detection -> Policy -> Existing Presence Mappings Only -> Write Changed Fields -> Readback -> Front Office Verify -> Audit`

`NO_CHANGE -> NO_WRITE`

A source outage/parser failure is `VERIFICATION_FAILED`.

It must never be converted automatically into OUT_OF_STOCK or quantity zero.

---

## 16. Dolibarr and MoneyWork boundaries

M99 owns canonical identity/knowledge/governance.

Dolibarr is operational ERP/CRM/warehouse.

Migration contract:

`Inspect -> Normalize -> Deduplicate -> Identity Map -> Supplier/Customer Map -> Dry Run -> Import -> Reconcile -> Audit`

MoneyWork and existing websites are reconciliation sources, not canonical masters.

Legacy IDs/history are preserved through mappings.

Warehouse semantics:

- supplier order -> reception -> M99 physical stock increase;
- customer order -> shipment/configured stock event -> M99 physical stock decrease.

Supplier external availability remains distinct from M99 physical stock.

CRM baseline remains:

`First call -> Offer -> Second call`

Customer 360 remains a later product-platform-dependent direction.

## 17. Security, audit and credentials

Never commit or expose:

- passwords;
- API keys;
- tokens;
- session secrets;
- private keys;
- runtime secrets.

Secrets must not appear in Git, logs or screenshots.

Operators do not see channel/B2B credentials.

Permissions are enforced server-side.

Operational DB files, DB backups, runtime audit JSONL, `.venv`, caches, temporary `.bak` patch backups and downloaded installer ZIP files do not belong in normal Git commits.

## 25. NEW DECISION - Self-Tested Release Process

**Decision ID:** `REL-SELFTEST-001`
**Effective:** 2026-09-06
**Status:** DECIDED

The operator's Windows CMD run must become the **final environment acceptance test**, not the first place where obvious installer defects are discovered.

Before a release package is delivered for real CMD testing, the assistant performs the maximum possible internal pre-release validation.

Required internal release path:

`INTERNAL RC`
`-> static/package audit`
`-> PowerShell AST/static analysis where PowerShell is used`
`-> reserved-variable / StrictMode hazard scan`
`-> BAT-to-script path validation`
`-> package manifest and hash verification`
`-> Git wrapper / failure-path simulation`
`-> Python compile`
`-> dedicated tests when runtime snapshot is available`
`-> maintained regression when runtime snapshot is available`
`-> secret/no-write-before-gates audit`
`-> FINAL candidate`
`-> operator Windows CMD acceptance`
`-> authorized live-environment acceptance where required`

Rules:

1. Do not create a user-facing revision for every minor installer bug.
2. Consolidate minor defects during the internal RC audit.
3. Do not weaken tests merely to obtain green.
4. Do not redesign accepted architecture merely to make a new feature easier.
5. Start functional releases from the latest known green synchronized baseline, unless an explicit recovery/superseding decision says otherwise.
6. Preserve all fixed governance and safety gates.
7. Real Windows acceptance remains mandatory for environment-specific behavior that cannot be faithfully reproduced elsewhere.
8. Live website/DB/ERP writes require explicit authorized flow and must retain duplicate guards, readback and audit.

This decision is additive and is specifically intended to **increase development speed without sacrificing stability**.

## 26. Release engineering implementation preference

To reduce PowerShell-specific failure surface, future one-click release packages should prefer:

`BAT launcher -> controlled Python release driver`

when practical.

PowerShell may still be used when Windows-specific capabilities require it, but it must pass AST/static checks before user delivery.

The release driver must:

- identify the exact repo;
- verify branch and expected baseline;
- verify clean working tree;
- verify synchronization;
- touch only an explicit allowlist;
- protect secrets and runtime artifacts;
- run appropriate compile/tests;
- stage only exact intended files;
- run `git diff --cached --check`;
- commit only after green gates;
- refetch before push;
- push only when remote parent has not changed;
- verify final HEAD == upstream and clean worktree.

No force push, hard reset, `git clean -fd`, automatic pull/rebase or credential embedding.

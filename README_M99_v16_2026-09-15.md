## 1. Визия и бизнес предназначение

M99 Knowledge Platform е централен слой за canonical identity, verified
product knowledge, supplier/manufacturer evidence, commercial
intelligence, content/SEO, publishing, synchronization, ERP/CRM
integration, audit и governance за M99 Group. Платформата не е само
scraper и не е uploader за един сайт. Целите са международно развитие,
минимален административен headcount, максимална безопасна автоматизация,
контрол на cash flow/stock и дългосрочна подкрепа на M99 Group Master
Plan 2036.

------------------------------------------------------------------------

## 2. Канали и destinations

NEW PRODUCT IMPORT винаги предлага explicit multi-select на target
destinations. Операторът може да избере един, няколко или всички
разрешени READY web channels и, когато workflow позволява, Dolibarr.
Няма автоматично "всички" по подразбиране. Реалният write set е
`REQUESTED ∩ AUTHORIZED ∩ READY`. `NOT_SELECTED != BLOCKED`. Daily
Existing Product Sync не използва нов target selection и никога не
създава липсващ channel mapping.

## 3. Canonical identity и lifecycle

M99 identity е независима от supplier SKU/reference, Manufacturer MPN,
EAN/GTIN, MoneyWork code, Dolibarr ID, channel product ID, title и URL.
Новият нормативен формат е `M99 ` + точно шест цифри; старите hyphenated
references се пазят само като legacy/compatibility. Идентичността никога
не се reuse-ва. ProductGroup lifecycle е
`draft -> active -> paused -> retired`. Hard DELETE е изключение:
operator approval + ръчно `DELETE` + audit. Identity се решава преди
content. States: NEW / EXISTING / AMBIGUOUS / UNRESOLVED.

------------------------------------------------------------------------

## 4. Supplier / Manufacturer / Brand / Evidence

Supplier и Manufacturer са отделни роли, дори когато една Organization
изпълнява и двете. Supplier Reference и Manufacturer MPN са различни
semantic fields, дори когато стойността им съвпада. Brand е отделен
canonical object. Нов Supplier/Manufacturer/Brand изисква Super Admin
governance. Evidence priority: exact official manufacturer -\> official
documentation/certificate -\> validated B2B -\> exact supplier -\>
verified internal data -\> operator -\> AI over verified facts.
Observation не става автоматично canonical truth. Durable manufacturer
evidence може да се reuse-ва само по exact governed scope, без
fuzzy/brand-wide inference.

------------------------------------------------------------------------

## 5. Operator UX и автоматизация

Операторът е бизнес потребител, не програмист. Нормалният workflow не
трябва да изисква Python, PowerShell, HTTP, JSON/XML, SQL, credentials
или вътрешни paths. Новият основен принцип е
`Human by exception, not by repetition`: повторяемите решения с одобрени
правила се автоматизират. За category/multi-product import няма
product-by-product typed confirmations. Всеки product/target се
класифицира машинно като AUTO_READY, NEEDS_REVIEW или BLOCKED.
Операторът одобрява batch-ready set и обработва само
exceptions/conflicts/high-risk anomalies/destructive actions.

------------------------------------------------------------------------

## 6. New Product Import и batch processing

Един engine трябва да поддържа 1 продукт, много продукти, една/много
категории, first N, only-new-to-M99 и manual selection без
product-specific code. Всеки import е auditable ImportJob. Category
workflow: supplier/source selection -\> category/product selection -\>
explicit target selection -\> automated
hydration/evidence/identity/price/VAT/content/images/variants/preflight
-\> Batch Review -\> publish only AUTO_READY -\> quarantine
NEEDS_REVIEW/BLOCKED -\> strict readback -\> Batch Quality Report.

------------------------------------------------------------------------

## 7. Publishing constitution

CREATE != UPDATE. Duplicate guard before CREATE. Mandatory readback
after every write. HTTP/API success != Product Quality PASS. Activation
requires authorization. Final category is operator-owned. Approved
identity/locked fields са защитени. CLI/BAT са development/diagnostic
tooling, normal operations стартират от M99 Admin. Автоматизацията е
fail-closed: failed critical gate блокира конкретния product/target;
unrelated AUTO_READY items могат да продължат, освен при systemic
failure.

------------------------------------------------------------------------

## 8. Цени: източник, ежедневно наблюдение и публикация

Supplier commercial price се наблюдава ежедневно за canonical products с
verified Supplier/Source mappings. Source priority за commercial facts:
validated B2B connector, ако е наличен; иначе exact supplier product
page. Category/search/competitor page не е достатъчно price evidence.
SupplierObservation пази source/product/variant identity, URL/resource,
observed_at, verified_at, price, currency, availability, changed_fields
и verification/provenance state.

M99 target selling price е customer-facing GROSS/VAT-included. Новото
business pricing правило е:
`M99 target GROSS = verified supplier benchmark GROSS × (1 - r)`, където
`r` е random процент от 1.00% до 1.70%. Процентът се генерира при
първоначално pricing и при verified supplier-price change. Ако benchmark
price не се е променил: `NO_CHANGE -> NO_WRITE` и не се прави gratuitous
re-randomization. При промяна pipeline е: SupplierObservation -\>
PRICE_CHANGED -\> approved pricing rule -\> market currency -\> VAT -\>
target GROSS -\> platform NET representation if required -\> API write
-\> readback -\> Front Office gross verification.
Suspicious/out-of-policy anomalies -\> NEEDS_REVIEW.

------------------------------------------------------------------------

## 9. VAT / данъчни правила

VAT е channel/market configuration и не се hardcode-ва универсално.
Standard VAT rule/rate се resolve-ва от конкретния target store/market.
Ако платформата пази NET, M99 изчислява platform NET от target GROSS.
`id_tax_rules_group=0` блокира production quality за стандартно облагаем
продукт. API/Back Office price alone не е достатъчен; след write се
проверява customer-facing Front Office gross price. 0.00 при очаквана
ненулева цена е PRICE_GATE FAIL.

------------------------------------------------------------------------

## 10. Content, SEO, AEO/GEO и benchmark

Content Engine работи върху verified Product Knowledge. Supplier prose
не се копира verbatim. Facts могат да са общи, но prose/SEO са
channel/market/language specific. AI може да структурира, пише и
превежда verified facts, но не измисля
standards/materials/stock/technical claims. Customer-facing content не
трябва да съдържа вътрешен M99 governance/evidence/debug текст. Meta
Description и Short Description са различни assets; normalized
similarity \< 0.75. Language purity е critical gate.

Benchmark: Amazon/Zalando/eBay за information hierarchy, scanability,
variants, images, specification clarity и buying information; Apple за
clarity, hierarchy, concise benefits и low-noise presentation; exact
official manufacturer source за factual accuracy; Stenso/Palltex и
релевантни местни конкуренти за terminology, assortment, price
positioning и content gaps без copying. Search benchmark се открива
динамично по country/language/query.

------------------------------------------------------------------------

## 11. Images

Image source priority: official manufacturer -\> verified supplier -\>
verified cached original source. Друг M99 channel не е master image
source само защото вече има правилната снимка. Pipeline: Discover -\>
Verify -\> Download -\> Relevance Check -\> Dedupe -\> Resize ~1200-1400
px -\> WebP -\> localized ALT -\> operator/policy review -\> Upload -\>
Association -\> Readback. Theme/logo/cart/search/header assets и
unrelated images се reject-ват. Variant-specific image relationship се
пази, когато source го доказва.

------------------------------------------------------------------------

## 12. Variants, combinations, availability и stock

Visible size != stock. Presence != stock. Supplier availability !=
M99-owned physical stock. Supplier status не създава invented quantity.
Numeric external quantity се пази само при reliable exact source
quantity. Variational product трябва да има точно една default
combination; cache/default pointer трябва да съвпада. Combination price
impact = 0 по подразбиране, освен при доказана реално различна variant
selling price. Out-of-stock variant не се delete-ва само защото е
временно unavailable.

------------------------------------------------------------------------

## 13. Daily Existing Product Sync

Daily Sync е отделен operational class от New Product Import. Всеки ден
се проверяват supplier/B2B price, availability, variants/sizes, product
changes и discontinuation. States: NO_CHANGE, PRICE_CHANGED,
AVAILABILITY_CHANGED, VARIANT_AVAILABILITY_CHANGED, PRODUCT_CHANGED,
SUPPLIER_DISCONTINUED, VERIFICATION_FAILED. Source outage/parser error =
VERIFICATION_FAILED, не OUT_OF_STOCK/0. Sync пише само changed fields
според policy и само към вече съществуващи allowed channel/ERP mappings;
не създава missing channel products.

------------------------------------------------------------------------

## 14. Product Quality Gate и readback

Critical gates включват IDENTITY, MANUFACTURER_EVIDENCE, SUPPLIER_MATCH,
PRICE, VAT, CURRENCY, LANGUAGES, CONTENT, SEO, TECHNICAL_FACTS, IMAGES,
ALT, VARIANTS, DEFAULT_COMBINATION, TEST/DRAFT or governed publication
state, READBACK, FRONT_OFFICE, NO_INVENTED_CLAIMS и NO_UNVERIFIED_STOCK.
Numeric score никога не override-ва failed critical gate. Batch Quality
Report трябва да показва success/readback counts и exception reasons.

------------------------------------------------------------------------

## 15. Dolibarr, warehouse, MoneyWork и CRM

M99 е canonical identity/knowledge/governance layer. Dolibarr е
operational ERP/CRM/warehouse. M99-owned physical stock: supplier order
reception -\> increase; customer shipment -\> decrease; variant-aware.
SUPPLIER_EXTERNAL / MANUFACTURER_EXTERNAL availability warehouses са
отделни от M99_PHYSICAL. MoneyWork и legacy sites са reconciliation
sources, не canonical masters. Preferred migration: Inspect -\>
Normalize -\> Deduplicate -\> Identity Map -\> Supplier/Customer Map -\>
Dry Run -\> Import -\> Reconcile -\> Audit. CRM foundation: First call
-\> Offer -\> Second call.

## 16. Security, RBAC и audit

Operators никога не виждат channel/B2B credentials. Secrets не се
commit-ват в Git, не се log-ват и не се показват в screenshots.
Permissions се enforce-ват server-side. Authentication direction: secure
password hashing, sessions/logout, timeout, failed-login protection,
reset workflow, login/logout audit, future 2FA. Central logs: Audit,
System, Supplier/B2B & Channel Integration, Security. Minimum context:
timestamp, severity, user, module, operation, entity, supplier/channel,
job_id, result, message, correlation_id.

# 30. GitHub Continuous Safe Checkpoint Governance — v16

**Decision status:** DECIDED / NORMATIVE
**Effective from:** 2026-09-15
**Baseline before this rule:**
`b9a3140b098287f600f7741c9f7a6bc6bc8aa0b9`

## 30.1 GIT-001 — Continuous Safe Checkpoint

Every successfully accepted M99 version or revision MUST finish with a
Safe Git Checkpoint.

Normative lifecycle:

`Development -> Self-Test / MAXSIM -> Windows Acceptance -> PASS -> Safe Git Checkpoint -> Push -> Verify origin/main -> Next Version`

Git checkpointing is part of the release lifecycle. It is not a separate
cleanup activity to be postponed until many files accumulate.

If any mandatory Git safety gate fails, there is NO commit and NO push.
The system reports the concrete blocker and preserves the working files.

## 30.2 GIT-002 — Small checkpoints

A governed checkpoint MUST be created after every accepted functional
revision or coherent accepted milestone. The platform MUST NOT
intentionally accumulate weeks of accepted source/documentation work
into one large manual Git operation.

The objective is small, auditable checkpoints with a clear relationship
between accepted functionality, tests, documentation, decision records,
Git commit and remote GitHub state.

## 30.3 GIT-003 — Runtime and secrets never enter Git

Runtime state and sensitive/local-only artifacts MUST remain outside Git
checkpoints.

At minimum the engine MUST exclude or block `var/**`, runtime job
sidecars, `.env` and real credential files, secrets/API keys, virtual
environments, caches, `__pycache__`, local databases, logs, temporary
files, backups and generated archives.

These exclusions SHOULD be enforced by `.gitignore` and MUST also be
verified before commit.

A source identifier such as `api_key`, `token` or `password` is not
itself a secret. Secret scanning MUST be value-aware and distinguish
identifiers from actual credential values.

## 30.4 GIT-004 — Maintained regression gate

The automatic checkpoint gate MUST run the maintained regression suites.

Current maintained automatic scope:

- `tests/`;
- `admin-platform/tests/`, when present.

Historical backup tests under `output/hotfix_backup/**` and live/manual
diagnostics under `scripts/**` that intentionally require credentials,
network access, Vault configuration or supplier authentication are
outside the normal unattended regression gate unless explicitly promoted
into maintained tests.

A maintained regression failure blocks commit and push.

## 30.5 GIT-005 — Documentation travels with accepted code

Architecture and governance documentation MUST be checkpointed together
with, or immediately after, the accepted implementation it describes.

Relevant documentation includes README master/history versions,
`DECISION_REGISTRY`, ADR records, machine-readable state/history,
governed configuration and tests proving the decision.

A material architecture/operating decision MUST NOT remain only in chat.

## 30.6 GIT-006 — Remote-parent protection

Immediately before push, the engine MUST fetch and verify the remote
parent. Push is allowed only when the expected remote baseline is still
valid.

If `origin/main` moved unexpectedly, the operation MUST stop safely.

The automatic process MUST NOT use force push, `reset --hard`,
`git clean`, uncontrolled merge, uncontrolled rebase or automatic
destructive conflict resolution.

## 30.7 GIT-007 — One-click operator workflow

The normal operator MUST NOT manually select dozens of files in GitHub
Desktop or execute Git commands.

After successful Windows acceptance, the target operator interaction is
at most one meaningful approval:

`SAVE M99 CHECKPOINT`

Long-term M99 Admin target:

`Save accepted version to GitHub`

Everything else is machine-executed: discover changes, classify
safe/runtime files, exact staging, documentation verification,
whitespace check, value-aware secret scan, compile smoke, maintained
regression, `git diff --cached --check`, audit report, fetch,
remote-parent verification, commit, push, readback and
`HEAD == origin/main` verification.

## 30.8 Permanent Safe Git Checkpoint Engine

The fixes proven during the 2026-09-14 checkpoint MUST become permanent
repository/platform behavior, not a sequence of temporary installers.

The permanent engine MUST incorporate:

1.  deterministic non-paged Git execution;
2.  trailing-whitespace validation;
3.  value-aware secret scanning;
4.  maintained-test scoping;
5.  runtime/local-only exclusion;
6.  exact staged-set audit;
7.  remote-parent protection;
8.  mandatory post-push verification.

The Safe Git Checkpoint Engine itself MUST have automated tests.

## 30.11 GIT-008 — Mandatory multi-format governance artifacts

Every new governed README/master checkpoint MUST be created and preserved in all mandatory representations at the same checkpoint.

Mandatory artifact set:
- human/source README in Markdown: `README_M99_vNN_YYYY-MM-DD.md`;
- machine-readable master record: `M99_MASTER_MACHINE_MEMORY_vNN_YYYY-MM-DD.json`;
- human Bulgarian Word document: `M99_All_Decisions_BG_vNN_YYYY-MM-DD.docx`;
- compatibility Word document: `M99_All_Decisions_BG_vNN_YYYY-MM-DD.doc`.

The four artifacts form one governed documentation set and MUST describe the same normative decision state. A new README version MUST NOT be considered documentation-complete if one of the mandatory representations is missing.

The machine-readable record MUST be structured for deterministic AI/machine ingestion and include at minimum: schema/version, checkpoint date, repository/baseline context, normative rules/decision registry, superseded decisions where applicable, current accepted state, release/Git governance, and integrity hashes for the companion artifacts when generated.

The `.docx` and `.doc` documents are the Bulgarian human-readable consolidated decision record from project start through the checkpoint. They MUST preserve the same normative rules without silently weakening or replacing prior accepted decisions.

The Safe Git Checkpoint Engine MUST verify that the complete mandatory artifact set exists before checkpointing a new master README version. Unless a file is explicitly classified as local-only, all four governance artifacts MUST be staged, committed and pushed together.

If generation or validation of any required representation fails, the documentation checkpoint status is `INCOMPLETE` and Git commit/push of that master documentation checkpoint MUST stop.

For every future master README version, this multi-format generation is automatic and is not a separate operator task.
